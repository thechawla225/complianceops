# 0016. Self-host metrics and logs: kube-prometheus-stack, Loki and Alloy, installed by Terraform

- **Status:** Proposed
- **Date:** 2026-11-07

## Context
Since Phase 08.1 every service exposes Prometheus metrics at `/metrics`: RED metrics with identical names in Python
and Go, plus domain metrics such as `sqs_publish_failures_total` and the notifier's heartbeat. Nothing collects them,
and logs exist only as `kubectl logs` output that disappears with the pod. Phase 08 needs both, in one place, for
dashboards (08.4), alerts (08.3) and the SLO (95% of requests under 300 ms).

## Decision
- **Metrics:** kube-prometheus-stack chart 92.22.0 (Prometheus Operator v0.94.2): Prometheus, Alertmanager, Grafana,
  kube-state-metrics and node-exporter.
- **Logs:** Loki chart 7.5.0 in single-binary mode, collected by Grafana Alloy (chart 1.15.0).
- **Installed by Terraform** (`non-persistent/monitoring.tf`) in a `monitoring` namespace, like Argo CD and Kyverno:
  platform comes up with the cluster. The namespace is outside sanctions-platform's default-deny, quota and Kyverno
  policies.
- **Scrape config ships with each service:** a ServiceMonitor in the gateway, transaction and screening charts, and a
  PodMonitor in the notifier chart (it has no Service). Prometheus selects monitors in every namespace
  (`*SelectorNilUsesHelmValues: false`), so a new service is scraped when its chart deploys.
- **NetworkPolicy:** transaction, screening and notifier allow ingress on their app port from pods labelled
  `app.kubernetes.io/name=prometheus` in the `monitoring` namespace only (one `from` block, so both must match).
  The gateway already accepts any source on 8000.
- **EKS control plane not scraped:** etcd, the scheduler and the controller-manager are managed by AWS and unreachable,
  and kube-proxy binds metrics to localhost. Their scrape jobs (and the alerts on them) are disabled.
- **Storage: emptyDir** for Prometheus (2-day retention) and Loki. The cluster is destroyed after every session.
- **Alloy reads logs through the Kubernetes API** (`loki.source.kubernetes`), one replica, no hostPath mounts. Labels
  are limited to namespace, pod, container and app.
- **Least privilege:** Alloy's role is cut to pods, pods/log and namespaces (the chart default also reads every Secret
  and ConfigMap); Loki's rules sidecar, which needs cluster-wide Secret access, is disabled.
- **Access:** `kubectl port-forward` only. Grafana's admin password is generated by the chart into a Kubernetes
  Secret, so it's never in Git or Terraform state.
- **Ordering:** Argo CD's apps depend on kube-prometheus-stack, so the ServiceMonitor/PodMonitor CRDs exist before the
  charts sync.

## Alternatives considered
- **Amazon Managed Service for Prometheus + Managed Grafana:** no Prometheus to run, but billed per sample and per
  user, needs a collector and IAM anyway, and is AWS-only. Self-hosted is the portable, interview-standard stack and
  what the CKA covers.
- **CloudWatch Container Insights + CloudWatch Logs:** native and simple, but per-GB log ingestion cost, and no
  PromQL for the app's RED metrics.
- **Promtail:** reached end of life on 2 March 2026; Alloy is its replacement.
- **Alloy as a DaemonSet tailing node log files:** the scalable pattern, but it needs hostPath mounts and a pod per
  node. At two nodes, one replica reading through the API is simpler and less privileged.
- **Loki in simple-scalable or distributed mode:** about 3x the memory, for volume this project will never reach.
- **EBS volumes (PVCs) for Prometheus and Loki:** survive pod restarts, but uninstalling a StatefulSet doesn't delete
  its PVCs, so every teardown could leave billed, orphaned volumes.
- **Loki on S3 (persistent state, IRSA):** logs would outlive the cluster, which is the right compliance answer for
  production audit logs. Deferred: it adds a bucket, a role and Checkov work that Phase 08 doesn't need yet.

## Consequences
- Metrics and logs are lost when the cluster is destroyed, or when the Prometheus/Loki pod is rescheduled.
- About 11 new pods and roughly 1.3 GiB of memory requests on two c7i-flex.large nodes (about 6.5 GiB usable);
  capacity is checked in the EKS session.
- CRD upgrades: Helm installs kube-prometheus-stack's CRDs on first install but doesn't upgrade them; a major chart
  bump needs its CRD upgrade step.
- Alertmanager runs with no receivers until 08.3 (Slack webhook via External Secrets).

## Results
Pending the EKS session (08.5): all 4 services' targets `up`, logs from sanctions-platform queryable in Grafana, and
memory headroom on the nodes.
